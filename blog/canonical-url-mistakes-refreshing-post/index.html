Canonical URL mistakes when refreshing a post

A canonical URL is the one address you want search engines to treat as the real home of a page. You declare it with a single line in the page's head: <link rel="canonical" href="...">. When a post has one clear home, every link, share, and bit of search history points at the same place.

Refreshing an older post is one of the best things a small software company can do with its blog. It is also the moment canonical mistakes tend to happen, because a refresh touches templates, slugs, and copies of the page at once. This post is for founders who approve posts rather than build the site. The goal stays the same as everywhere on this blog: more qualified people engaging with the product every month while the team keeps building. A post that quietly loses its address works against that.

What a canonical tag actually does

Think of it as a label that says "if you find this content in more than one place, this is the original." It matters because the same post can often be reached several ways: with and without a trailing slash, with tracking parameters on the end, over http and https, or through a print or preview view.

Two things are worth knowing before you worry about it:

  • It is a strong hint, not a command. Search engines usually follow it, but they can pick a different address if other signals disagree, such as internal links and the sitemap pointing somewhere else.
  • Most pages should point at themselves. A self-referencing canonical, where the page names its own address, is the normal case. It closes the door on stray duplicate versions.

That is why this blog now prints a self-referencing canonical on every page, including the home page and the blog index. It took one line in the publish template and a one-time backfill of the pages that were already live.

Mistake 1: changing the slug during a refresh

The slug is the readable last part of the address, like /blog/refresh-or-rewrite-aging-post/. When a post gets a new title, it is tempting to give it a matching new slug. That turns a refresh into a new page with no history, and every old link now leads to an error.

The refresh-or-rewrite post makes the rule plain: a refresh keeps the URL. The title tag and H1 can change; the address should not. If the topic has drifted so far that the old slug is misleading, that is a sign you are rewriting, not refreshing, and the kill-or-rewrite call comes first.

If a slug truly must change, the old address needs a permanent redirect to the new one, and the new page's canonical must name the new address. Do both in the same publish. A canonical alone does not move readers who arrive at the old link.

Mistake 2: a template that points every page at the home page

This one usually comes from a well-meant shortcut. Someone adds a canonical tag to the shared page layout with a fixed address, often the home page, so every post now tells search engines "the real version of me is the home page."

The result is that posts can stop showing up on their own, because they have each declared themselves a copy of something else. A refresh is often when someone opens the template, so it is often when this gets introduced.

The fix is to build the canonical from each page's own slug, never to hard-code it. On this blog the publish script fills it in from the same slug it uses to write the file, so the two cannot disagree.

Mistake 3: the canonical, the sitemap, and the internal links disagree

Search engines weigh the canonical against other signals. If the canonical says /blog/post/ but the sitemap lists /blog/post without the slash, and half your internal links use a third version with a tracking parameter, you are sending mixed messages.

Pick one form and use it everywhere:

SignalShould use
Canonical tagThe full https address, same trailing-slash style as the rest of the site
Sitemap entryThat exact address
Internal linksThat exact address, or a relative link that resolves to it
Shared links in email or socialThat exact address, before any tracking parameters

A refresh is a good time to check this, because refreshes usually add a few new internal links. The reciprocal linking checklist and the orphan-post cleanup both assume links point at the canonical form.

Mistake 4: pointing the canonical at a page that redirects or no longer exists

Canonicals rot. A post was moved last year, the redirect was added, but the canonical on a related page still names the old address. Now the "real home" of that page is a redirect, or worse, an error page.

The rule is simple: the canonical address should load directly with a normal success response. Not a redirect, not a missing page, not a page that is blocked from search. This is something a script can check in seconds by fetching the canonical address and looking at the response, so it belongs in a gate rather than in a founder's review.

Mistake 5: a refreshed copy published next to the original

Sometimes a refresh is drafted as a brand-new post, published, and the original is left up "for now." Two pages now cover the same thing with mostly the same words. Each claims to be canonical for itself, and they compete with each other.

There are two clean outcomes. Either merge the new material into the original address and publish over it, or, if the new piece is genuinely different, give it a distinct angle, its own title tag, and its own meta description. "Leave both up and sort it out later" is the one outcome to avoid.

A pre-publish check for refreshed posts

None of this needs a founder to read HTML. It needs a few yes-or-no checks that run before anything goes live, the same way the quality gates before you publish work and the way the one-H1 check was added:

  1. Same slug as before? If not, is there a redirect from the old address in the same publish?
  2. Canonical present and built from the slug? Not a fixed address in the template.
  3. Canonical address matches the sitemap entry exactly? Same scheme, same trailing slash.
  4. Canonical address loads directly? A normal success response, not a redirect or error.
  5. No second live page covering the same topic? If there is, merge or differentiate before publishing.

The first and last items are judgment calls an agent can flag and a founder can answer in a sentence. The middle three are mechanical and should fail closed: if the check cannot confirm them, the post does not go out.

What the founder actually approves

For a refresh, the approval read should take about as long as any other post. The founder confirms the update is accurate and still sounds like the company. The address question should arrive pre-answered: "Refresh of an existing post, same URL, canonical checked." If the agent proposes a slug change, that is the one line that deserves a second look, because it is the one change that is hard to undo.

Keep the address boring and stable, let the content get better, and the post keeps everything it has already earned.
