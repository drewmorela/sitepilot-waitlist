When two H1s sneak into a draft (and the QA gate that catches them)

An H1 is the main heading of a page. In Markdown it is the line that starts with a single #. In HTML it is the <h1> tag. On a blog post it should say one thing: what this page is about. When a draft ends up with two of them, the page now has two answers to that question.

This post is for founders of small software companies who approve blog posts rather than write them. The goal behind every post on this blog stays the same: more qualified people engaging with the product every month while the team keeps building. A clean heading structure is a small part of that. It helps a scanning reader, a screen reader, and a search engine agree on what the page covers.

The fix is not a style debate. It is a yes-or-no check that runs before anything goes live.

Why one main heading matters

A page with one H1 has a clear top. Everything under it is a section, marked with H2s, and smaller points sit under those as H3s. That outline is what the fail-closed outline approach builds before a single paragraph is written.

A second H1 breaks that shape in three ways:

  • Readers lose the thread. Someone skimming sees two headings the same size and has to guess which one is the real topic.
  • Assistive tools get a confusing map. People using screen readers often jump between headings. Two top-level headings make the page feel like two documents.
  • The topic signal blurs. The H1 usually matches the title tag and the cluster slice the post was written for. If a second H1 names a different idea, the page now points two ways. The title tag post covers why that match matters.

Search engines can usually cope with more than one H1, so this is not about a penalty. It is about a page that says one thing clearly, which is what turns a visitor into a qualified reader.

How a second H1 sneaks in

Nobody types two H1s on purpose. They arrive through ordinary steps in a publishing session:

  1. A pasted section. Someone copies a block from another doc or an old post, and its heading comes along as # instead of ##.
  2. A template that already has a title. The page layout prints the post title as an <h1>, and the Markdown body starts with its own # line too. Now the rendered page has two.
  3. An agent draft that restates the title. A writing tool, human or AI, opens with the headline, then adds a "summary" heading at the same level.
  4. A heading drawn with equals signs. In Markdown, a line underlined with === is also an H1. It is easy to miss in a review because it does not start with #.
  5. A refresh that adds a new top section. When an older post gets a refresh instead of a rewrite, a new "Update" heading sometimes lands at the top level.

Each of these is a two-second mistake that a founder reading for meaning will not notice. That is exactly why it belongs in an automated gate, not in the approval read.

The gate: exactly one H1, checked before publish

The quality gates before you publish on this blog already required a page to have an H1 and at least two H2s. That rule caught a missing heading. It did not catch an extra one.

So the structure gate now says: exactly one H1. The check works like this:

StepWhat it does
Ignore code blocksA # inside a code sample is not a heading, so fenced code is skipped
Count # headingsLines that start with one # and a space
Count HTML H1sAny <h1> written directly into the body
Flag underlined headingsA line followed by ===, which Markdown also treats as an H1
DecideOne H1 passes. Zero or two-plus fails, with the count in the message

A fail names the row and the number, for example "exactly one H1 allowed, found 2." The writer fixes it by demoting the extra heading to an H2 or removing it. The founder never has to open the file.

When we added this rule, we ran it against every post already published here and checked each live page's HTML. Each post had one H1. That is the boring result you want: the gate costs nothing on clean posts and only speaks up when something slips.

Check the rendered page, not only the draft

The Markdown can be clean and the published page can still have two H1s, because of the template issue in step 2 above. The draft gate cannot see the layout. So a second, smaller check runs after publishing: fetch the live page and count <h1> tags in the HTML.

If the draft says one and the live page says two, the problem is in the template. Fix it once there and every future post is covered. This is the same idea as checking that a page returns a working response before you call it shipped.

Where this fits in the approval flow

The founder's job in approving without becoming the editor is to answer a few yes-or-no questions about fit and accuracy. Heading structure should never be one of them. Put it where machines are good:

  1. The writer finishes the draft from the one-screen content brief.
  2. The structure gate runs: one H1, at least two H2s.
  3. The rest of the gates run: originality, readability, brand fit, anti-spam, internal links.
  4. Only a draft that passes all of them reaches the founder.
  5. After publishing, the live page is fetched and the H1 count is checked again.

If a draft keeps failing structure after two rounds, that is often a sign the outline itself is unclear. At that point it may be time to kill the draft instead of rewriting it.

Start this week

  1. Open your last three published posts and count the main headings on the live page.
  2. If your template prints the title as an H1, make sure post bodies start at H2.
  3. Add "exactly one H1" to your pre-publish checklist, and automate it if you can.
  4. Add a post-publish check of the live HTML for the same count.
  5. Keep the founder's approval read for meaning, not formatting.
